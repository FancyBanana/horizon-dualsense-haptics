## ZIG 0.16 FACTS (learned, reuse)
- `std.c.Stat` = `void` on Linux in 0.16 (its `switch (native_os)` has no linux branch →
  `else => void`). Same for `std.posix.Stat` (`.linux => void`). There is NO `stat`/`fstat`
  in std.c or std.posix on Linux at all. Use glibc `extern "c"` + your own struct mirror.
- `std.c.timespec` = `linux.timespec` (`extern struct { sec, nsec }`) — still valid.
- `std.os.linux.mmap` takes `prot: PROT` where PROT is an arch-packed struct
  (e.g. `os.linux.PROT__struct_14734`), not `c_int` → `@bitCast`.
- `std.c.PROT` on Linux is the packed struct TYPE, so `.READ`-style member access is invalid;
  construct `std.c.PROT{ .READ = true }` and `@bitCast` to c_int for comparisons.
- 0.16 translate-c renames (already applied to lib/c.zig): `std.zig.c_builtins.*` →
  `std.zig.c_translation.builtins.*`; `cast`/`promoteIntLiteral`/`sizeof` → `helpers.*`;
  `MacroArithmetic.*`/`Macros.*` → `helpers.*`.
- Main/io idioms: `pub fn main(init: std.process.Init)`, `std.process.Args.Iterator.init(...)`,
  `init.io`, `file.readStreaming`, `readFileAlloc(io, path, gpa, .limited(n))`.
- Unused `c_int` returns (e.g. `pw_properties_set`) are hard errors → `_ =`.
- `@ptrCast` to a stricter-alignment pointer requires `@ptrCast(@alignCast(x))`.
- `std.hash.crc.Crc32` exists (= `std.hash.crc.Crc32IsoHdlc`, poly 0x04c11db7, non-reflected) —
  likely does NOT match the kernel's `crc32_le` used for DualSense BT; verify before using.
- Module CLI binding: `--dep name -Mname=file` must be in that order.

## BLUETOOTH PLAN (user asked for planning ONLY — do not implement yet)
- Feasibility: YES. Triggers + rumble are HID-output-report driven and work over BT.
  Only *native* USB-audio haptics is USB-only, but this project does PC-side audio→rumble and
  writes HID rumble bytes, so BT is purely a transport/format change.
- BT output report: **78 bytes, report ID 0x31**:
  - byte 0 = `0x31`
  - byte 1 = sequence: high nibble = seq counter (0-15, increment every report), low nibble = 0
  - byte 2 = `0x10` (magic tag, `DS_OUTPUT_TAG`)
  - bytes 3-49 = same 47-byte common section as the current USB report's bytes 1-47
  - bytes 50-73 = zeros
  - bytes 74-77 = CRC32 LE
- CRC (kernel `dualsense_send_output_report`):
  `crc = ~crc32_le(crc32_le(0xFFFFFFFF, {0xA2}, 1), report[0..74])`, stored little-endian.
  Seed `PS_OUTPUT_CRC32_SEED = 0xA2`. Report is ignored if CRC wrong.
- Detection: `matchesHidId` in `src/dualsense.zig:200` already parses the `HID_ID=` bus field
  but discards it — capture it (0x03 = USB, 0x05 = Bluetooth) and pick the report format.
- Changes: add `BtOutputReport` (78B) to `src/dualsense.zig` + a seq counter + crc32 helper;
  `src/haptics.zig` only fills common fields so needs no logic change.
- Caveats: BT effective poll ~125 Hz (throttle writes); keep an idle-report keepalive; Windows BT
  is a separate mess (driver ownership + known trigger-disable quirk needing feature report 0x05)
  — keep BT Linux-first.
- Reference: `linux/drivers/hid/hid-playstation.c` — full copy fetched at
  `/tmp/opencode/hid-playstation.c` (constants: `DS_OUTPUT_REPORT_BT=0x31` size 78,
  `DS_OUTPUT_REPORT_USB=0x02` size 63, `DS_OUTPUT_TAG=0x10`, seq in `DS_OUTPUT_SEQ_NO` bits 7:4,
  common section is 47 bytes). The project's 48-byte USB report matches the kernel common layout
  offset-for-offset (report_id byte 0, common bytes 1-47).
